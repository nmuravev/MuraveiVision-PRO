## 🚀 PRE-SPRINT ACTIONS (КРИТИЧНО)

**Эти задачи должны быть выполнены ДО начала Спринта 1.**

### M0: Миграция данных (Data Migration)
**Задача:** Обеспечить бесшовный переход с `.pkl` на новый формат.
**План:**
1. Написать скрипт `backend/scripts/migrate_catalog_v1_to_v2.py`.
2. Скрипт запускается один раз при старте приложения (в `lifespan`), если обнаруживает старые файлы.
3. Создает бэкап `*.pkl.bak` перед конвертацией.
4. Конвертирует numpy arrays в base64 или bytes (в зависимости от выбранного формата).
5. **Атомарность:** Новый файл пишется полностью в временное имя, затем атомарно заменяется через `os.replace()`.
6. **Версионирование:** Добавить поле `"version": 2` в корень нового файла для будущего отличия v1/v2/v3.
**Важно:** Если конвертация не удалась — приложение не должно падать, а логировать ошибку и продолжать работу в режиме "read-only" для старых данных.

### T1: Стресс-тесты (Load Testing)
**Задача:** Валидация фиксов гонок (Race Conditions) и блокировок.
**Инструмент:** `locust` (air-gap safe, работает локально).
**Сценарий:**
- 50-100 concurrent users.
- Эмуляция одновременных SSE подключений (P0-1).
- Эмуляция brute-force атак (P0-3).
**Це��ь:** Убедиться, что фикс P1-2 (DB) не убивает throughput.

### Rollback Strategy
- **Frontend:** Откат через redeploy старого билда (мгновенно).
- **Backend:** Изменения в схеме БД должны быть обратимыми (backward compatible).
- **Pickle/JSON:** Если новый формат ломает чтение, добавить fallback на старый формат при инициализации каталога.

### ✅ Pre-Start Checklist (перед началом Спринта 1)

#### 1. Проверка зависимостей для Air-Gap
Убедитесь, что колеса (*.whl) для `msgpack`, `portalocker` и `locust` уже скачаны и лежат в локальном репозитории/папке проекта.
```bash
# Сделать на машине с интернетом заранее:
pip download msgpack portalocker locust -d ./wheels
```
**Важно:** В air-gap среде `pip install` в момент разработки не сработает.

#### 2. Тест "Отката" (Rollback Test) для M0
Перед запуском миграции на продакшене проведите тест:
1. Запустите скрипт миграции.
2. Вручную повредите новый файл (или удалите его).
3. Попробуйте запустить приложение со старым бэкапом `.bak`.
4. Убедитесь, что код fallback действительно работает и читает старый формат.

#### 3. Нагрузка для PoC P1-2
При тестировании блокировок БД эмулируйте не только успешные запросы, но и сценарий, когда один поток держит lock долго (например, имитация медленной записи), чтобы убедиться, что очередь запросов не переполняет память.

#### 4. Frontend Bundle Size
При внедрении Immer (P2-11) и исправлении парсера SSE (P1-14) следите за размером бандла. В air-gap сетях доставка больших обновлений фронтенда может быть медленной.

#### 5. Конфигурация окружения
Добавить переменные `SSE_IDLE_TIMEOUT`, `GPU_TENSOR_POOL_SIZE` в `.env.example`.
Убедиться, что CI/CD или процесс деплоя подхватывает эти переменные.

#### 6. Frontend Node.js
Проверить версию Node.js/npm в изолированной среде. Совместима ли она с последними версиями библиотек, которые могут понадобиться для фикса SSE?

#### 7. Зависимости (Wheels) — КРИТИЧНО
Убедитесь, что колеса (*.whl) для `msgpack`, `portalocker` и `locust` уже скачаны и лежат в локальном репозитории/папке проекта.

**Важно:** В air-gap среде `pip install` в момент разработки не сработает.

#### 8. Скрипт миграции (M0)

## 🔴 P0 — КРИТИЧЕСКИЕ (11)

### P0-1: SSE Stream Never Terminates (Connection Leak / DoS)
**Файл:** `backend/api/recon.py`  
**Источник:** Audit #1  
**Обновление v2.0:** Таймаут 300s слишком велик для защиты от DoS.  
**Фикс:**
1. Сделать таймаут конфигурируемым через env var `SSE_IDLE_TIMEOUT` (default: 60s).
2. Внедрить Heartbeat (ping/pong) каждые 15s. Если клиент не отвечает — закрывать соединение.
3. Отправить `Connection: close` заголовок.  
**Сложность:** 3ч

### P0-2: Orphaned asyncio.create_task()
**Файл:** `backend/api/network.py`  
**Источник:** Audit #1  
**Проблема:** `asyncio.create_task(worker.push_local_messages())` без сохранения ссылки → Task может быть GC'd до завершения → потеря сообщений.  
**Фикс:** Сохранять ссылки в set: `self._tasks.add(task)`, чистить через `task.add_done_callback(self._tasks.discard)`.  
**Сложность:** 2ч

### P0-3: Non-atomic fail_count in record_failed_login ✅ DONE
**Файл:** `backend/services/db.py`  
**Источник:** Audit #1  
**Обновление v2.0:** Атомарный SQL не защищает от `sqlite3.OperationalError: database is locked`.  
**Фикс:**
1. Атомарный SQL: `UPDATE lockouts SET fail_count = fail_count + 1 ...`.
2. Добавить `retry logic` (3 попытки с backoff) при `sqlite3.OperationalError`.  
**Сложность:** 2ч
**Коммит:** `514b62c`  
**Тесты:** `backend/tests/test_lockout_atomicity.py` — 6/6 passed (10 concurrent threads)

### P0-4: Path Traversal in recon_asset ✅ DONE
**Файл:** `backend/services/recon_scanner.py`  
**Источник:** Audit #1  
**Проблема:** `asset_path()` использует `startswith` вместо `relative_to()` → потенциальная path traversal.  
**Фикс:** Заменить на `target.relative_to(job_dir.resolve())` с catch ValueError.  
**Сложность:** 1ч
**Коммит:** `8ba206b`  
**Тесты:** `backend/tests/test_path_traversal.py` — 5/5 passed

### P0-5: GPU Memory Leak в sam3_engine
**Файл:** `backend/services/sam3_engine.py`  
**Источник:** Audit #2  
**Обновление v2.0:** Простое `del` не освобождает память мгновенно из-за CUDA caching allocator.  
**Фикс:**
1. Внедрить пул тензоров (tensor pool) для переиспольз��вания памяти.
2. Вызывать `torch.cuda.empty_cache()` периодически (не после каждой итерации, чтобы не убить FPS), например, раз в N инференсов или при критической нехватке памяти.
3. **Конфигурация:** Размер пула должен быть настраиваемым через env var `GPU_TENSOR_POOL_SIZE`. Разные модели (SAM3 vs YOLO) требуют разного объема памяти.  
**Сложность:** 4ч

### P0-6: OOM Fallback не восстанавливает устройство
**Файл:** `backend/services/yolo_engine.py`  
**Источник:** Audit #2

**Фикс:** Сохранять `_original_device`, пытаться восстановить CUDA через `empty_cache`. Retry logic с max 3 attempts.

### P0-7: Stale Running State в recon_scanner

## ⚠️ Air-Gap Constraints

### ❌ НЕ ДОПУСКАТЬ (нарушают air-gap):
- **Prometheus + Grafana** — требуют network для scrape
- **SQLAlchemy async (aiosqlite)** — требует async database driver
- **Network-dependent monitoring** — любые cloud services
- **External package installs at runtime** — все зависимости должны быть в wheels/

### ✅ ДОПУСТИМО (air-gap safe):
- **In-memory metrics** — histograms, counters в RAM
- **GPU memory management** — torch.cuda APIs локальны
- **Batch processing** — локальная обработка
- **File-based locks** — `portalocker` работает локально
- **SQLite WAL** — встроенный механизм, не требует network

## ⚠️ Observability & Rollback

### Observability (JSON Logs)
Для отлова специфических ошибок в будущем добавить структурированное логирование:
- Логи в формате JSON.
- Поля: `timestamp`, `level`, `module`, `error_type`, `message`.
- **Correlation ID:** Для каждого запроса генерировать уникальный ID и передавать его через все сервисы (если есть цепочка вызовов) и в логи. Критически важно для отладки проблем в асинхронной среде, где запросы перемешиваются.
- Отдельный handler для `sqlite3.OperationalError` (P0-3).

### Rollback Strategy
1. **Frontend:** Откат к предыдущему коммиту (git revert).
2. **Backend DB:** Изменения в схеме БД должны быть `ADD COLUMN` (never `DROP`/`MODIFY` без миграции).
3. **Catalog Format:** Если новый формат не читается — fallback на старый формат при инициализации.

1. **P1-2 (Thread-safe DB)** — самый рискованный фикс, может потребовать рефакторинга всех DB функций. **PoC обязателен.**
